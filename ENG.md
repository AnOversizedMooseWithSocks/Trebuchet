# Trebuchet Engineering Guide

## Purpose

This document describes how Trebuchet is built today and how to evolve it safely. It is intentionally implementation-facing: modules, runtime boundaries, long-running operation safety, tests, release constraints, and suggested architecture for the v2 wallet/SPA/Discovery direction.

## Current Architecture

Trebuchet is currently a local Electron app built from an Express web app.

```text
Electron main process
  main.js
    starts local Express server on a free port
    opens BrowserWindow to local server
    owns menus, safe external links, update checks, safeStorage bridge

Local Express backend
  server.js
    serves public/
    exposes /api/*
    coordinates Solana, Raydium, Metaplex, swap, journals, reports, prefs

Browser frontend
  public/index.html
  public/app.js                  generated bundle
  public/modules/*.js            source modules for app.js
  public/api.js                  legacy/session wrapper; current bundle also includes wrapper

Native helpers
  c/*
  c/build/*
    vanity keygen / VRF / tweetnacl helpers

Release and package tooling
  scripts/*.mjs
  .github/workflows/*
  electron-builder config in package.json
```

The architecture is pragmatic: the app began as a web app, and Electron packages the same static frontend plus local API server. That means most renderer code can use ordinary `fetch('/api/...')` calls and does not need Electron IPC.

## Important Source Files

### Runtime

- `main.js`
  - Electron entrypoint.
  - Picks/starts local server.
  - Creates `BrowserWindow`.
  - Adds context menus.
  - Handles safe external URL opening.
  - Checks GitHub releases for updates.
  - Uses `safeStorage` through `secretStore.js`.

- `server.js`
  - Main backend/API surface.
  - Owns route handlers, validation, operation mutexes, progress maps, demo-mode branching, launch journals, pending wallets, and long-running orchestration.

- `public/modules/*.js`
  - Canonical frontend sources.
  - `public/app.js` is generated by concatenating these modules in `scripts/build-app-js.mjs`.
  - Do not edit `public/app.js` directly for v1 behavior.

- `public/v2/*`
  - Current untracked v2 wallet-app mockup.
  - Static HTML/CSS/JS prototype, separate from generated v1 bundle.

### Solana and Launch Domain

- `tokenService.js`
  - Temporary wallet generation.
  - QR code generation.
  - Token creation with Metaplex.
  - Balance checks.

- `lpService.js`
  - Raydium CLMM pool and position creation.
  - Funding estimation.
  - Fee tiers.
  - Known quote/flywheel token support.
  - Lock and Fee Key recording.

- `swapService.js` / `swapMath.js`
  - Quote-token acquisition and Raydium route support.
  - Swap retry and failure classification.

- `walletHelpers.js`
  - Multi-token balance checks.
  - NFT, SPL token, SOL sweeping.
  - Airdrop execution.

- `launchJournal.js`
  - Recoverable launch-state persistence.

- `launchReportService.js`
  - Launch report payload and publishing.

- `demoChainService.js`
  - Simulated launch execution for Demo Mode.

### Local State and Security

- `rpcConfig.js`
  - Saved RPC endpoints and active endpoint selection.

- `userPrefs.js`
  - Local UI/user preferences.

- `pendingWallets.js`
  - Recovery entries for launch wallets.

- `secretStore.js`
  - Uses Electron `safeStorage` when available, falls back to tagged plaintext.

- `validators.js`
  - Token metadata and supply normalization.

## Session and Local API Security

The frontend obtains a session token from `/api/session` and attaches it to same-origin `/api/*` requests through `x-trebuchet-session`. This protects the local API from accidental cross-site invocation.

Security-relevant details:

- External URLs in Electron are restricted to `https:`.
- Image proxying validates protocol, host/IP, and redirect chain.
- Long-running launch operations are guarded per wallet.
- Airdrops have their own in-flight guard.
- Secrets are stored through `safeStorage` where possible.
- Release notes disclose unsigned artifacts and checksums.
- Dependency upgrades must respect the SDK compatibility matrix in `SECURITY.md`.

## Long-Running Operation Safety

The backend uses per-wallet in-memory mutexes to reject concurrent launch operations:

- Token creation.
- Quote-token acquisition.
- Pool creation.
- Resume launch.
- Asset transfer.

The user can reload the renderer while the backend operation continues, so UI button disabling is not sufficient. Server-side locking returns HTTP `409` with code `OP_IN_FLIGHT`.

Engineering rule: every new long-running wallet-mutating endpoint must either:

- claim/release the per-wallet launch operation mutex, or
- justify why it is read-only or independent.

## Launch Lifecycle State

The on-chain launch lifecycle is not transactional. Some operations can succeed permanently while later operations fail. Therefore Trebuchet must persist enough facts to resume safely:

- Token mint and metadata URI.
- Authority revocation facts.
- Pool IDs.
- Position NFTs.
- Lock transactions.
- Fee Key NFT mints.
- Fee Key transfer status.
- Failed phase and recoverable failure details.
- Airdrop delivery/failure results.

Do not implement “retry from scratch” for work that may already have landed on-chain.

## Demo Mode Parity

Demo Mode is not just a UI mock. It should mirror real API response shapes closely enough that:

- users can learn the full flow,
- frontend regressions appear in demo,
- launch reports generated in demo exercise the same report structure,
- resume/transfer/airdrop surfaces stay testable.

When changing a real launch payload, update `demoChainService.js` and corresponding tests.

## v2 Architecture Direction

The v2 mockup currently lives under `public/v2/` and is standalone. To turn it into production code, avoid bolting everything into one static file forever. Recommended direction:

```text
public/v2/
  index.html
  styles.css
  app.js                 prototype only

future:
  src/v2/
    app-shell/
    wallet/
    launch/
    discovery/
    extension/
    shared/
```

### v2 Product Surfaces

- Launch desk.
- Wallet portfolio.
- Transaction queue.
- Extension approval window.
- Permissions.
- History.
- Discovery.

### v2 Integration Plan

1. Keep static v2 as a UX prototype until requirements stabilize.
2. Extract v2 state and rendering into modules before connecting real APIs.
3. Define a typed client contract for launch/wallet/discovery APIs.
4. Reuse existing backend endpoints where possible.
5. Add browser tests for every v2 navigation item and narrow/mobile layout.
6. Treat v2 as the future primary shell; keep v1 available as Classic until feature parity.

## SPA/WASM Direction

The browser/WASM goal exists partly to avoid macOS unsigned app friction. A browser-only build cannot assume Node/Electron APIs, and should start with the parts of Trebuchet that are naturally browser-safe.

### Candidate Browser-Compatible Layers

- Pure math:
  - `lpMath.js`
  - `swapMath.js`
  - `lpDistribution.js`
  - `lpFeeTiers.js`
  - `validators.js`
  - token metadata layout helpers
- UI and report rendering.
- Demo Mode.
- Token configuration and preflight validation.
- Discovery scoring when backed by browser-fetchable data.
- Wallet-adapter transaction signing after explicit simulation.

### Harder Browser Layers

- Key storage and secret recovery.
- Native C vanity keygen/VRF helpers.
- Local file persistence.
- Direct Electron `safeStorage`.
- Long-running launch orchestration without a backend process.
- Raydium/Metaplex flows that depend on Node-only transitive packages.
- Some SDK flows if dependencies require Node built-ins.

### Recommended WASM/SPA Plan

1. Create a pure-domain package boundary.
2. Add tests that run in Node and a browser-like environment.
3. Identify SDK imports that block bundling.
4. Move local persistence behind adapters.
5. Implement SPA Demo Mode first.
6. Implement real signing through browser wallet adapters second.
7. Only then evaluate full launch execution in-browser.
8. Keep full Raydium/Metaplex launch orchestration on the Electron/local-backend path until browser compatibility is proven end-to-end.

## Browser Extension Direction

If Trebuchet becomes a Chrome extension, treat it as a wallet/security product:

- Minimal permissions.
- Clear connected-site approval UI.
- Explicit simulation before signing.
- Session-scoped site permissions.
- No silent transaction signing.
- Human-readable transaction summaries.
- Strict origin display.
- Local storage encrypted where the browser platform allows it.
- No arbitrary raw transaction approval without simulation and clear effects.

Extension UX should align with v2:

- connected site topbar,
- transaction queue,
- approval popover,
- policy controls,
- history,
- Discovery as a read-only/evaluation surface.

Allowed extension actions for the first real version:

- Connect/disconnect site.
- Sign message with strict origin display.
- Approve simulated transactions.
- Submit wallet-safe transfers.
- Approve explicit Trebuchet launch-session transactions.

Disallowed until proven safe:

- Silent signing.
- Raw opaque transaction signing.
- Launch execution initiated by arbitrary third-party sites.
- Fee Key, liquidity, or authority actions without explicit effect summaries.

## Discovery Engineering Direction

The mock Discovery view currently uses local static data. Production Discovery needs a data contract and scoring model. The MVP should be evidence-first and should not include ratings, bookmarks, notes, or social voting.

### Proposed Data Model

```js
{
  mint: string,
  symbol: string,
  name: string,
  score: number,
  status: 'pass' | 'watch' | 'fail',
  liquidity: {
    poolCount: number,
    topPoolPercent: number,
    quoteDiversity: string[],
    totalDepthUsd: number | null
  },
  holders: {
    count: number | null,
    top10Percent: number | null
  },
  authority: {
    mintRevoked: boolean,
    freezeRevoked: boolean,
    metadataRevoked: boolean | 'disclosed'
  },
  provenance: {
    launchReportUri: string | null,
    lockedPositions: number,
    feeKeyMints: string[]
  }
}
```

### Scoring Requirements

- Scores must be explainable.
- Missing data should reduce confidence, not silently pass.
- Paid promotion must not influence score.
- User ratings/social signals must not exist in the Discovery MVP.
- Watch/fail reasons should be visible in the UI.

### Data Source Options

- Local index from Trebuchet launch reports.
- On-chain verification of authorities, pools, locks, holders, and liquidity.
- Public token/pool/indexer APIs for tokens without Trebuchet reports.
- User-supplied mint lookup.
- Optional hosted indexer only after the local/indexed evidence model is stable.

## Release Engineering

Release behavior is documented in `docs/releasing.md`.

Current flow:

- PRs run tests and package smoke builds.
- Merge to `main` triggers auto-version/tag.
- Tag workflow builds:
  - macOS arm64 DMG.
  - macOS x64 DMG.
  - Windows NSIS installer.
  - Windows portable EXE.
  - Linux AppImage.
  - Linux deb.
- `SHA256SUMS.txt` is attached.
- GitHub Package is published.
- `website/` is deployed by FTP.

Signing constraints:

- macOS signed/notarized only when Apple signing and notarization credentials are present.
- Without Apple credentials, macOS artifacts are unsigned test artifacts and macOS may show “app is damaged.”
- Windows artifacts are signed only when Windows signing credentials are present.
- Any unsigned desktop test artifact marks the GitHub Release as prerelease.

## Dependency Policy

Do not run `npm audit fix --force` casually.

The Solana/Raydium/Metaplex dependency graph contains compatibility-sensitive packages. Follow `SECURITY.md`:

- Keep `@solana/spl-token` compatible with current APIs.
- Validate Metaplex/Irys line changes end-to-end.
- Run syntax/tests.
- Use live low-risk RPC smoke for SDK upgrades touching launch execution.

## Implementation Guidelines

- Prefer editing module sources over generated artifacts.
- Keep backend route handlers small enough to test, extracting pure helpers where possible.
- Keep every long-running operation resumable or explicitly non-resumable with user-facing consequences.
- Validate user input before chain calls.
- Preserve launch report backwards compatibility where possible.
- Keep demo payloads aligned with real payloads.
- Avoid hidden network calls in UI code.
- Treat browser pages and remote metadata as untrusted.
- Keep v2 flat and information-dense; do not regress into nested cards.
- Block unsafe preallocation/support configurations by default; allow advanced override only with explicit consequence acknowledgement.
